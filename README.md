# aya-co-re-issue

## Prerequisites

1. stable rust toolchains: `rustup toolchain install stable`
1. nightly rust toolchains: `rustup toolchain install nightly --component rust-src`
1. (if cross-compiling) rustup target: `rustup target add ${ARCH}-unknown-linux-musl`
1. (if cross-compiling) LLVM: (e.g.) `brew install llvm` (on macOS)
1. bpf-linker: `cargo install bpf-linker` (`--no-default-features` on macOS)

## Build & Run

Use `cargo build`, `cargo check`, etc. as normal. Run your program with:

```shell
cargo run --release
```

Cargo build scripts are used to automatically build the eBPF correctly and include it in the
program.

## Cross-compiling on macOS

Cross compilation should work on both Intel and Apple Silicon Macs.

```shell
cargo build --package aya-co-re-issue --release \
  --target=${ARCH}-unknown-linux-musl \
  --config=target.${ARCH}-unknown-linux-musl.linker=\"rust-lld\"
```
The cross-compiled program `target/${ARCH}-unknown-linux-musl/release/aya-co-re-issue` can be
copied to a Linux server or VM and run there.

## The issue

This repo reproduces [aya-rs/aya#722](https://github.com/aya-rs/aya/issues/722): `task_struct`
generated by `aya-tool` bakes in field offsets from whatever kernel it was generated on.
`aya-ebpf`'s `bpf_probe_read_kernel` does a plain offset read, with no BTF CO-RE relocation, so a
binary compiled against one kernel's `vmlinux.rs` silently fails to read the right offset on a
kernel with a different `task_struct` layout — `bpf_probe_read_kernel` returns `Err`, and the `?`
in `try_aya_co_re_issue` (`aya-co-re-issue-ebpf/src/main.rs`) returns early, so nothing is logged.

### Confirming the CO-RE relocation table is empty

`clang` only emits CO-RE relocation records into `.BTF.ext` for reads that use
`__builtin_preserve_access_index` (what `bpf_core_read!`/aya's future CO-RE support would use).
`bpf_probe_read_kernel` as called here doesn't, so the relocation table is empty even though the
program reads two struct fields. Confirm it after building:

```shell
EBPF=$(find target -path '*bpfel-unknown-none/release/aya-co-re-issue' | head -1)
readelf -x .BTF.ext "$EBPF" | head -5
```

```
Hex dump of section '.BTF.ext':
 NOTE: This section has relocations against it, but these have NOT been applied to this dump.
  0x00000000 9feb0100 20000000 00000000 44000000 .... .......D...
  0x00000010 44000000 74090000 b8090000 00000000 D...t...........
```

The `.BTF.ext` header's last 4-byte field on the second hex line (offset `0x1c`, `core_relo_len`)
is `00 00 00 00` — zero CO-RE relocations were generated, confirming the struct offsets are frozen
into the binary at compile time instead of resolved against the running kernel's BTF.

### Reproducing "shows nothing" on a different kernel with Vagrant

Tested with:

- Build/host kernel: `7.0.0-31-generic`
- Guest kernel where the program produces **no output**: `6.1.0-47-amd64` (Debian 12,
  `debian/bookworm64` Vagrant box)

Steps:

1. Build the static binary so it runs unmodified on the guest's glibc:

   ```shell
   rustup target add x86_64-unknown-linux-musl
   cargo build --package aya-co-re-issue --release \
     --target=x86_64-unknown-linux-musl \
     --config=target.x86_64-unknown-linux-musl.linker=\"rust-lld\"
   ```

2. Bring up the VM (requires `libvirt`/`vagrant-libvirt`; the project's `Vagrantfile` uses the
   libvirt provider and rsyncs the repo to `/vagrant` in the guest):

   ```shell
   vagrant up --provider=libvirt
   ```

3. SSH in and confirm the kernel differs from the one `vmlinux.rs` was generated on:

   ```shell
   vagrant ssh -c 'uname -r'
   ```

4. Run the binary and, from a second `vagrant ssh` session, trigger `execve`s (e.g. `ls`):

   ```shell
   # session 1
   vagrant ssh -c 'sudo RUST_LOG=info /vagrant/target/x86_64-unknown-linux-musl/release/aya-co-re-issue'

   # session 2, while session 1 is running
   vagrant ssh -c 'ls / >/dev/null'
   ```

   On a kernel with matching `task_struct` layout you'll see `My parent: <ppid>` lines. On
   `6.1.0-47-amd64` with a `vmlinux.rs` generated elsewhere, session 1 prints nothing.

5. Tear down when done:

   ```shell
   vagrant destroy
   ```
